# ADR-008: Typed response contracts and request tracing

Status: Accepted for VERTEX Vision RC branch

## Decision

The VERTEX Vision staging API treats database responses as untrusted transport input.
Views command results are projected through a versioned allowlist before they are returned
to web or Android clients.

The v1 projector is implemented in
`vision/modules/views/response-contract.mjs`. It validates the expected lifecycle state
for each reviewed command and exposes only booking/unit/correlation fields plus the
cleaning fields required by checkout/cleaning commands.

Every API response generated by the staging Worker receives an `X-Request-ID`.
Successful Views commands additionally receive `X-Correlation-ID`, copied from the
domain correlation identifier committed with the command transaction.

## Why

Input validation alone is insufficient. A later SQL change, view, function or upstream
adapter could accidentally add private notes, tokens, internal flags or other fields to a
JSON response. The transport boundary must explicitly define what is allowed to leave the
backend.

Request IDs and domain correlation IDs solve different problems:
- request ID identifies one HTTP attempt;
- correlation ID identifies the business workflow/aggregate across retries and events.

The API may generate many request IDs for retries while preserving one domain correlation
ID for the committed operation.

## Rules

1. Command responses are projected, not passed through.
2. Unexpected command lifecycle states fail closed as upstream errors.
3. Database-only/private fields are never forwarded by default.
4. Request IDs are generated by the gateway, not accepted from request bodies.
5. Correlation IDs come from the committed domain response.
6. Reads continue to use their own allowlisted DTO projection.
7. Logging may record IDs and operation names, but never bearer tokens or sensitive payloads.

Production remains gated on real staging Auth/database E2E and explicit approval.
