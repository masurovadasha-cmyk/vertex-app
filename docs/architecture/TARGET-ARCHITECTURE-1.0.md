# VERTEX VISION — целевая архитектура 1.0

Дата: 30 сентября 2026. Статус: техническое предложение для реализации, не production-релиз.
Основа анализа: `vision-foundation-rc-0.1`, снимок `50fc7df742687d9b5a6dea2a329f7f6874367e80`.
Документ дополняет ADR-002 и сохраняет бизнес-ограничения ADR-003. Никакие миграции, настройки облака, приложения и production в рамках этого документа не изменяются.

## 1. Архитектурное решение

VERTEX VISION — один продукт с общим ядром и независимыми бизнес-модулями. На первом этапе это модульный монолит: один управляемый цикл выпуска, один PostgreSQL-кластер на среду, тонкий HTTP API и отдельный процесс асинхронных обработчиков из той же кодовой базы. Разделение API и фонового исполнителя не означает 19 микросервисов.

В RC 0.1 активен только Views Hotel & Apartments. Внутри Views входят Dashboard, Calendar, Units, Guests, Bookings, Check-in, Check-out, Tasks, Cleaning, Maintenance read/workflow и базовое чтение финансовых данных. Остальные 18 направлений остаются Coming Soon, без запуска старых демо-функций. Существующая SQL-цепочка с Cleaning сохраняется как проверенная основа и совместимость, но не означает активацию отдельного бизнес-модуля Cleaning.

JARVIS — отдельные репозиторий, данные, секреты и развёртывание. Будущая интеграция допускается только через внешние контрактные API с ограниченными полномочиями и аудитом, не через прямой доступ к базе или административный обход.

Не вводить сейчас Kubernetes, Kafka, service mesh, отдельную БД для каждого направления, многорегиональную запись бронирований, универсальный BPM-конструктор или event sourcing всей системы. Их польза должна быть доказана измерениями и требованиями, а не количеством названий в Hub.

## 2. Что подтверждено исходниками, а что проектируется

В рассмотренном снимке уже есть: реестр 19 направлений с Views Active; staging Worker с передачей проверяемого пользовательского токена в Supabase; PostgreSQL-команды, RLS, версии записей, receipts повторных команд, история, аудит и transactional outbox. Документы явно отличают локальный переключатель ролей от настоящего входа.

`vision/platform/registry.cjs` возвращает `sharedDatabase: not-connected`, `authenticated: false`, `productionReady: false`. Это не свидетельство подключённой облачной эксплуатации. `vision/backend/worker.mjs` читает максимум 50 строк через `select=*`, не предоставляет пагинацию и объединяет несколько транспортных задач в одном обработчике. Их следует разделить и заменить явными DTO, не называть это уже выполненной работой.

Исходная `vision_users` привязывает UUID пользователя к одному tenant. Для будущего SaaS требуется отдельная модель глобальной идентичности и членства в нескольких tenant. Перед миграцией нужно сверить все последующие SQL-изменения, а не менять первую миграцию задним числом.

Этот обзор архитектурный и выборочный: он не является аудитом каждой строки, нагрузочным тестом или подтверждением безопасности production.

## 3. Неизменяемые правила

1. Tenant — граница изоляции данных, организация — бизнес-структура, property/unit — объект размещения, module — набор функций. Это разные понятия.
2. Наличие карточки модуля не даёт доступ к его API. Проверяется пересечение release state, tenant installation, готовности capability и разрешения пользователя.
3. У каждого бизнес-факта один владелец и один авторитетный путь записи. localStorage, календарная проекция и кеш не подтверждают бронь.
4. Успешная критическая команда означает commit бизнес-данных, аудита и receipt в одной транзакции. Сбой обязательного аудита отменяет команду.
5. Сеть может потерять ответ после commit. Повтор с тем же ключом возвращает прежний результат, а не создаёт новый объект.
6. Сообщения могут приходить повторно и не по порядку. Глобальное exactly-once не обещается.
7. Откат приложения не равен откату данных. Удаление пользовательских записей не является стратегией отката релиза.

## 4. Логическая и физическая схема

```text
Web / Android
    |
    v
Cloudflare: статические ресурсы + единый вход API
    |
    v
VISION API: auth -> authorization -> module gate -> command/query handler
    |                                      |
    |                                      +-> Views read models
    v
Views application / domain + узкие контракты Core
    |
    v
PostgreSQL: Core + Views + audit + receipts + outbox
    |
    v
Outbox dispatcher -> очередь -> обработчики / проекции / адаптеры

Объектное хранилище: отдельный доступ к фото и вложениям
Supabase Auth: поставщик идентичности, не источник бизнес-полномочий
```

Один публичный продукт не требует одного исполняемого файла. API и consumers масштабируются отдельно, оставаясь в общем репозитории. Не каждый внутренний вызов должен становиться HTTP-запросом.

Начальная платформа исполнения сохраняет Cloudflare Workers и PostgreSQL/Supabase. Для Workers действуют ограничения CPU, памяти и соединений; бесплатный план нельзя считать доказанной базой высоконагруженного SLA [S4]. Тяжёлые экспорты и обработку изображений выносить из синхронного запроса. Регион БД и размещение динамической обработки выбирать по измеренной задержке и требованиям к данным, не только по географии CDN.

## 5. Ядро не должно знать все бизнес-процессы

| Владелец | Что принадлежит ему | Что ему не принадлежит |
|---|---|---|
| Core Identity / Access | subject, tenant membership, org scope, permissions, module installations | даты проживания, тарифы, статусы брони |
| Core Parties / Directory | минимальный tenant-scoped customer ID, разрешённые связи и контакты | единое неограниченное досье гостя для всех компаний |
| Core Work | общий task envelope, назначение, срок, связь с доменным объектом | универсальная схема всех отраслевых процессов |
| Core Reliability | audit writer, idempotency, outbox, inbox, trace context | бизнес-решение «можно ли заселить гостя» |
| Views | properties, units, inventory, bookings, stays, housekeeping, maintenance, financial read models | внутренние таблицы Travel, Taxi или Restaurant |
| Будущие модули | собственные агрегаты, правила, таблицы и разрешения после отдельного релиза | прямые изменения бронирований Views |

`Booking`, `CleaningJob`, `ServiceOrder` и будущий `Ride` — разные агрегаты. Нельзя использовать один универсальный `orders.status` как единственный источник всех их состояний. Общая категория для списка задач допустима как проекция; доменный статус остаётся у владельца.

Существующую `vision_command` не удалять. Сохранить за версионированным фасадом совместимости. Новые команды Views получают собственные имена и доменный контракт. Расширение общего SQL-switch десятками несвязанных бизнес-процессов прекращается.

Core не импортирует Views, Views не импортирует чужой runtime. Разрешены зависимости на public contracts; межмодульную оркестрацию выполняет application-координатор. Прямые SQL-записи в частные таблицы другого модуля запрещены. В одной БД вызов документированной функции Core в общей транзакции допустим и не требует распределённой транзакции.

## 6. Структура кода и постепенный переход

Целевая структура, а не требование немедленного перемещения всех файлов:

```text
apps/
  web/                    # shell, маршруты, composition root
  api/                    # HTTP, auth, DTO, обработка ошибок
  worker/                 # outbox, consumers, reconciliation
  android/                # оболочка и платформенные адаптеры
packages/
  core/                   # identity/access/directory/work/reliability
  contracts/              # OpenAPI, события, публичные типы
  ui/                     # компоненты, accessibility, визуальные токены
modules/
  views/
    domain/               # сущности и правила без HTTP/DOM/SDK
    application/          # use cases и порты
    infrastructure/       # SQL/RPC, object storage, внешние адаптеры
    presentation/         # экраны и ViewModels
    contracts/            # публичная поверхность Views
  registry/               # метаданные Coming Soon
infra/
  cloudflare/             # раздельные конфигурации сред
  database/migrations/    # упорядоченные неизменяемые миграции
  release/                # manifest, gate, rollback runbooks
tests/
  contracts/ integration/ e2e/ load/ architecture/
docs/architecture/
```

Новый код — TypeScript с strict checking; UI — React с поэкранной миграцией и lazy loading. Это выбор для будущей реализации, а не заявление о текущем стеке. Транспорт API остаётся тонким; бизнес-правила не привязывать к конкретному роутеру или ORM.

Текущие `vertex/dist`, `vision/platform`, `vision/backend` сохраняются до переноса владельцев исходников. Старые browser globals доступны только через один legacy adapter; новые модули не создают новые глобальные зависимости. Сначала выделяется исходный frontend-каталог, затем `dist` становится только build output. Генератор не должен подменять проверяемые исходники или редактировать ожидания тестов ради зелёного CI.

Контракты HTTP и событий имеют версию. Старый Android поддерживается в объявленном окне совместимости; breaking changes требуют новой API-версии. Web и Android используют один UI build, но native storage, auth callback и разрешения проверяются отдельно. Не объявлять новый package ID бесшовным обновлением старого приложения.

## 7. Данные и идентичность

Начать с одной PostgreSQL-БД на среду и логических владельцев таблиц. Физическое разделение по схемам `core`, `views`, `integration`, `audit` — целевое; существующие `public.vision_*` переносить только отдельными совместимыми миграциями.

Целевая модель: проверенный Auth subject -> глобальный principal -> tenant memberships -> organization/resource scopes. Сопоставление identity использует проверенный issuer и subject. Один человек может иметь несколько членств, но не получает общий доступ ко всем tenant автоматически.

Для Vertex Group первоначально допустим один tenant и несколько организаций. Это техническая граница, не автоматическое юридическое разрешение обмениваться персональными данными между компаниями. Иерархия подразделений не наследует права без явного правила.

Каждая tenant-owned строка содержит `tenant_id`; связи защищены составными ключами `(tenant_id, id)`. Строки Views содержат также конкретную организацию/объект, где нужен более узкий доступ. Глобальные справочники являются явными исключениями. Кеши, idempotency и inbox также включают tenant scope. Собственник квартиры — субъект с доступом к назначенным units, а не superadmin всего tenant.

Минимальные агрегаты Views:

- Property / Unit: стабильный ID, timezone, вместимость, видимость и связи с организацией.
- InventoryReservation: единый календарный ресурс для брони, временного hold и жёсткой блокировки размещения.
- Booking / Stay: коммерческая бронь отдельно от фактического проживания.
- HousekeepingJob / MaintenanceIncident: работа отдельно от состояния доступности номера.
- FinancialReadModel: начислено/оплачено/остаток с происхождением, временем актуальности и валютой.

Не соединять паспортные сведения и рабочие задачи уборщицы одной публичной выборкой. Контакты и документы выдаются отдельными узкими DTO. Большие вложения — в приватном object storage, в БД только метаданные и ссылки. До реальных персональных данных утвердить разрешённые регионы, обработчиков, сроки хранения и удаления; это отдельный compliance gate, не правовое заключение этого ADR.

## 8. Бронирование и конкурентность

Для посуточного размещения период — `[check_in_date, check_out_date)` в календаре property. Фактические события check-in/out — UTC timestamps плюс timezone объекта. День выезда не является занятой ночью; уборка и время готовности номера проверяются отдельными правилами.

Единая таблица inventory должна исключать пересечение активных резервов одной квартиры внутри tenant. PostgreSQL поддерживает range types и exclusion constraints для этого [S1]. Концептуальное ограничение: `EXCLUDE (tenant_id WITH =, unit_id WITH =, stay_range WITH &&) WHERE state IN (HELD, CONFIRMED, BLOCKED)`. Реализация требует проверенного расширения `btree_gist`, NOT NULL, непустого диапазона и локальных тестов; эта запись не является готовой миграцией.

Проверка свободных дат в UI предварительная. Два одновременных запроса могут её пройти, но commit допустим только для одного конфликтующего резерва. Второй получает безопасный доменный конфликт. Нельзя полагаться на process-local mutex, кеш или SELECT-then-INSERT без ограничения БД.

Истёкший hold освобождается явным транзакционным изменением состояния. Не использовать `now()` в предикате индекса. Cleanup и inline-expiry работают под согласованной блокировкой; задержка уборки hold может временно уменьшить доступность, но не должна вызвать overbooking. Продление/перенос брони меняет резерв атомарно; блокировки нескольких units берутся в стабильном порядке.

Параллельное редактирование: команда содержит `expected_version`; UPDATE затрагивает только ожидаемую версию. Конфликт требует повторного чтения и решения пользователя, не last-write-wins. Повтор после потери ответа использует прежний idempotency key и сначала проверяет сохранённый результат при актуальных правах, а не генерирует новый ключ.

Цена фиксируется в booking price snapshot. Суммы — целые minor units или точный decimal с явной валютой; в JSON большие целые передаются строкой. Валюты нельзя складывать без отдельной операции конвертации с зафиксированным курсом и источником. Финансовый read layer RC не равен полноценной бухгалтерии или платёжной системе.

## 9. Транзакционная граница и события

Пример check-out:

```text
BEGIN
  проверить principal, module gate и право check_out
  проверить receipt повторной команды и ожидаемую версию
  завершить Stay и обновить авторитетное состояние Views
  пометить housekeeping readiness DIRTY
  создать одну связанную задачу turnover через контракт Core
  записать audit + outbox + receipt
COMMIT
```

Требуемая задача создаётся в этой же транзакции; отправка уведомления не входит в неё. Unique business key, например `(tenant, stay, task_type)`, дополнительно защищает от повторного создания задачи. Ошибка очереди после commit не откатывает состоявшийся выезд.

После commit dispatcher берёт outbox с lease, отправляет сообщение и отмечает только передачу транспорту. Consumer записывает inbox-дедупликацию и собственное изменение в одной транзакции, затем подтверждает сообщение. Для нескольких потребителей нужна доставка по отдельным очередям либо явная fan-out-таблица, а не один общий флаг «всё доставлено».

Контракт события содержит `event_id`, `event_type`, `schema_version`, `tenant_id`, `organization_id`, `aggregate_id`, `aggregate_version`, `occurred_at`, `correlation_id`, `causation_id` и минимальный payload. Passport, пароль, bearer token и код двери в события не входят.

Cloudflare Queues предоставляет at-least-once; consumer обязан выдержать дубли [S3]. Глобальный порядок не требуется: stale aggregate versions игнорируются там, где допустимо, разрывы версий восстанавливаются повторным чтением/сверкой. Для пошаговых side effects нельзя просто отбросить отсутствующее промежуточное событие.

Внешняя отправка email или платёж не атомарна с нашей БД. Использовать стабильный provider idempotency key, журнал попыток и reconciliation. Если провайдер не поддерживает дедупликацию, нельзя обещать отсутствие повторных внешних эффектов. Retry — ограниченный exponential backoff с jitter, затем DLQ и управляемая повторная обработка. Ретенция inbox/receipts согласуется с максимальным временем redelivery и ручного replay; удаление старого receipt не должно разрешать повторный бизнес-эффект.

## 10. Доступ и HTTP-контракты

RC сохраняет простой путь: browser/mobile -> VISION API -> Supabase PostgREST/RPC с пользовательским access token. Идентичность проверяется доверенным Auth-слоем. Для следующей оптимизации локальная проверка JWT по JWKS требует проверки signature, issuer, audience, expiry и стратегии ротации; она не заменяет актуальную проверку membership и отзыва полномочий.

Supabase RLS сочетается с SQL grants. Секретные service-role ключи не должны обслуживать пользовательские чтения; привилегированные функции требуют явной авторизации, фиксированного search_path и ограниченного EXECUTE [S2]. Существующий SECURITY DEFINER — сознательное исключение, а не доказательство, что RLS применяется внутри функции к её владельцу. Runtime не получает роль владельца миграций.

Разрешения: собственник — назначенные объекты и разрешённые финансовые поля; менеджер — операции своей организации; cleaner — только назначенные задачи без финансов/документов; technician — назначенные инциденты; quality — проверка чужой работы; guest — явно связанные брони/заявки; auditor — чтение в разрешённом scope. Главный владелец тоже использует именованные права, MFA и аудит, а не скрытый bypass.

Cookie-сессии Web: HttpOnly/Secure, CSRF-защита для команд. Mobile: защищённое native-хранилище и PKCE flow. Не переносить production bearer token в localStorage. Выбранный способ входа внедряется и тестируется отдельно; демо-профиль не становится пользователем.

Целевой API имеет явные команды и DTO: `/api/v1/views/bookings`, `/bookings/{id}/check-in`, `/bookings/{id}/check-out`, `/units/{id}/availability`, `/tasks`, `/finance/summary`. Legacy `/api/commands` обслуживается адаптером. Новый API не допускает произвольные имена таблиц, select или SQL-фильтры от клиента.

Idempotency scope: `(tenant, principal, command_type, key)` с canonical payload hash и семантическим response. Для изменённого payload — 409; недоступных объектов — согласованная политика 403/404 без утечки; API недоступен — 503; лимит клиента — 429. Read pagination — cursor по стабильной паре `(created_at, id)`, лимит 50 по умолчанию и 100 максимум. Calendar запрашивается по ограниченному диапазону дат, не выгружает все брони.

## 11. Масштабирование и эксплуатация

Нагрузочные цифры ниже — предлагаемый проверочный профиль, не результаты тестирования и не гарантия тарифа. Наборы данных: 100, 1 000 и 10 000 квартир; разное число организаций, гостей и исторических записей. RC steady: 50 динамических запросов/с, из них 10 команд/с, 30 минут. Burst: 250 запросов/с, из них 25 команд/с, 10 минут. Отдельно 100 конкурирующих попыток одной брони и тест шумного tenant. Генератор нагрузки не должен сам ограничивать результат незаметно.

Стартовые цели из фиксированного региона нагрузки: read p95 <= 500 мс, command p95 <= 800 мс, 5xx < 0,1%, outbox p95 <= 10 с. Измерять end-to-end с реальным Auth; p99, CPU, pool wait, lock wait и backlog публикуются тоже. Конфликты 409 не считать 5xx, но их долю отслеживать отдельно. Предлагаемые availability/RPO/RTO: 99,9% в месяц / 15 минут / 4 часа; заявлять выполнение только после выбора тарифа, backup coverage и restore drill.

Порядок масштабирования: query plans и tenant-first indexes -> устранение N+1 и лишних round trips -> пагинация и проекции -> bounded concurrency и pool budget -> кеш публичного каталога -> отдельные consumers -> read replica для допускающих lag отчётов -> выделение доказанного узкого модуля. Брони, права и немедленное read-after-write не читать с отстающей реплики.

Ограничения по tenant/user/endpoint, request size, времени SQL и очередям обязательны. Нагрузка одного tenant не должна захватывать все DB connections. Для direct SQL возможен один проверенный слой pooling, но нельзя вслепую соединять несколько пулеров или переносить user claims между соединениями. Текущий HTTP RPC не требует открытия отдельного TCP-соединения каждым Worker.

Публичные фото и статические ресурсы кешируются. Приватные брони, контакты, финансы и authorization responses — no-store по умолчанию. Календарь/Realtime — уведомление об изменении и повторное чтение, не независимый источник истины. Offline production допускает черновик с явным pending, но не подтверждённую бронь без сервера.

`/livez` показывает жизнеспособность процесса. `/readyz` проверяет совместимость конфигурации/схемы и обязательный путь БД без раскрытия деталей; Auth end-to-end проверяется отдельным synthetic monitor. Не делать проверку всех внешних поставщиков на каждый liveness-запрос. Сбой уведомлений — degraded capability, не ложная недоступность всей системы бронирования.

Логи содержат request/trace/correlation ID, tenant, command, длительность и безопасный error code, но не payload гостя/токены. Метрики используют низкокардинальные labels; booking_id и user_id не становятся метками временных рядов. Audit хранит необходимый минимум и не равен debug-log. Триггеры append-only защищают от приложения, но не от superuser: для усиления доказательности нужен отдельно защищённый экспорт, согласованная retention и проверка доступа.

## 12. Одна цепочка выпуска

GitHub Actions становится единственным владельцем production-публикации. Конкурирующая автоматическая публикация из Cloudflare Workers Builds не должна независимо обходить этот gate; способ перевода существующей интеграции согласуется отдельным инфраструктурным изменением. Здесь её настройки не меняются.

Поток: source SHA + frozen lockfiles -> статические/контрактные/DB/RLS тесты -> build один раз -> staging-конфигурация -> synthetic Auth E2E и load smoke -> manifest и hashes -> approval -> production upload без смены трафика -> проверки совместимости -> promote конкретного version ID -> live hash/API/capability checks.

Cloudflare различает версию Worker и deployment; загрузка версии может выполняться без её немедленного назначения на трафик [S5]. Staging и production используют одинаковые code/static bytes, но разные явно учтённые bindings/secrets. Поэтому их Worker version IDs не обязаны совпадать. При promotion нельзя незаметно пересобрать другой frontend из изменившегося master.

Manifest содержит source commit, code/static SHA256, dependency lock digest, migration checksums, диапазон совместимых схем, module states, среды и bindings без значений секретов, Worker version ID, APK checksum/signing fingerprint и результаты проверок. Android release signing key хранится отдельно; debug-сертификат не используется как production-подпись.

Production approval принадлежит Фирдавсию или Дарье в рамках отдельно выданного разрешения. GitHub environment supports required reviewers, но доступность зависит от плана и видимости репозитория [S6]; нужно проверить фактическую настройку. При её отсутствии внедряется эквивалентный ручной gate, а не мнимое «защищено». Никаких токенов в чате и полного account-admin для CI.

Миграции: expand -> безопасный backfill -> switch -> contract в следующем релизе. Уже применённые SQL-файлы не редактируются. Один migration runner с lock и ledger; ожидаемая схема проверяется до deploy. Восстановление резервной копии проверяется на отдельной среде, включая доступность файлов и Auth-зависимостей.

Откат Worker не восстанавливает связанную БД/ресурсы [S7]. Старый API должен оставаться совместимым с expand-схемой. Разрушительные изменения и удаление bindings запрещены в релизе, для которого обещан мгновенный rollback. Full database restore — процедура аварийного восстановления с возможной потерей новых данных, не штатный автоматический rollback.

## 13. План реализации и критерии приёмки

| Этап | Изменение | Критерий завершения |
|---|---|---|
| A. Базовый снимок | Сверить master/RC, версии, реестр, ADR и существующий UI; сохранить legacy | Один воспроизводимый build; Views Active, 18 Coming Soon; никакие PII не импортированы |
| B. Разделение ядра | composition root, typed ports/DTO, ownership map, architecture checks | Core не импортирует бизнес-модули; нет обходных глобальных/SQL-зависимостей |
| C. Реальный Views | units/inventory/bookings/stays и узкие команды, настоящая auth/RLS | Два browser sessions, реальные тестовые учётные записи; чужие tenant/org/unit недоступны |
| D. Целостность и процессы | конкурентные брони, check-in/out, turnover, maintenance, finance read | Один победитель гонки; retry без дубля; checkout + DIRTY + task + audit атомарны |
| E. Фон и восстановление | outbox/inbox, DLQ, reconciliation, backup/restore | Crash до/после enqueue/commit/ack не теряет бизнес-команду; replay контролируем |
| F. Release gate | SLO/load evidence, environment policy, manifest, approval, rollback | Проверен staging; источник и опубликованные bytes совпали; восстановление подтверждено |

Все расширения после RC требуют отдельной активации направления. Будущий модуль должен иметь владельца, public contracts, permissions/RLS, миграции, tests, observability и rollback plan. Только после этого меняется Coming Soon.

Минимальный негативный тест-пакет: чужой tenant, другая организация внутри tenant, непривязанный собственник, неназначенная задача, revoked membership после входа, запрет self-approval, прямой вызов Supabase в обход UI, массовое назначение запрещённых полей, changed-payload replay, потерянный ответ после commit, истёкший hold, stale version, повторный webhook, частичный сбой outbox, исчерпание DB pool и сбой object storage. Выполнять на настоящем PostgreSQL и staging; PGlite не заменяет проверки нескольких соединений и платформенных интеграций.

## 14. Открытые решения и пределы уверенности

До production не установлены: реальные объёмы трафика и бизнес-пиков; согласованный бюджет и поддержка; выбранный разрешённый регион БД и файлов; фактический Auth/backup SLA; способ платёжной/OTA интеграции; кто операционно принимает инциденты. Они не мешают принять границы модулей, но запрещают обещать конкретную пропускную способность и отказоустойчивость.

Исходная реализация SQL-команд сохраняется до доказанного эквивалентного переноса. Не дублировать полный state machine в TS, SQL и UI независимо: правила имеют владельца, UI только предварительно проверяет ввод, SQL гарантирует инварианты и атомарность. Генерируемые контракты и parity tests фиксируют допустимое дублирование проверок.
